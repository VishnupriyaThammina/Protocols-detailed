Who's involved in Kerberos?
Three main entities communicate to get you access to a resource
🖥
CLIENT
Your computer. You are trying to access something — a file share, a database, an application — running on another machine in the network.
🏛
KDC
Key Distribution Center — the central trusted authority. Lives on the Domain Controller. Everyone trusts it. It verifies identities and issues access tickets.
🗄
SERVICE
The thing you want to access. Could be a file server, web app, database, or any network resource. It trusts the KDC to verify who you are.
The Core Idea

Your computer and the service don't trust each other directly. Both trust the KDC. The KDC acts as the trusted middleman — like a passport authority that both sides recognize.

What makes it secure

Your password never travels across the network. Instead, Kerberos uses encrypted tickets to prove who you are. If someone intercepts the traffic, they can't steal your password.

Where you see it

Windows Active Directory uses Kerberos for everything — logging into a computer, accessing file shares, Exchange, SQL Server, SharePoint. It's the backbone of enterprise authentication.

Step 1 — Authentication: Proving identity to the KDC
Client → KDC/AS (AS-REQ)  ·  KDC/AS → Client (AS-REP with TGT)
🖥 Client — before sending anything
① Alice types her password
e.g. P@ssw0rd123!
② Client runs MD4 on the password
Result = NTLM Hash (16 bytes)
This hash = Alice's secret key. Never leaves her machine.
③ Client encrypts current timestamp
🔑 Encrypted with: Alice's NTLM hash
Sends to KDC: username + Enc(NTLM_hash, timestamp)
This is called Pre-Authentication (AS-REQ)
🏛 KDC/AS — what it does
① Looks up Alice's NTLM hash in Active Directory
AD stores every user's NTLM hash — the KDC retrieves Alice's copy
② Decrypts the encrypted timestamp
If it decrypts correctly AND timestamp is within 5 min → identity confirmed
③ Sends back AS-REP (two parts)
Part A: TGS Session Key  🔑 Encrypted with: Alice's NTLM hash
→ Alice CAN decrypt and read this
Part B: TGT  🔑 Encrypted with: KRBTGT hash
→ Alice CANNOT read — only KDC holds the KRBTGT hash
⚠ Why timestamp?
Valid only 5 min → replaying a captured packet later won't work. All machines must sync clocks (NTP).
★ AS-REP Roasting
If pre-auth is disabled for an account, KDC skips step ① and returns a TGT to anyone → crack Part A offline.
★ Pass-the-Hash
Steal Alice's NTLM hash → use it directly to authenticate. No need to know the actual password.
Step 2 — KDC issues the TGT (Ticket Granting Ticket)
AS-REP: KDC sends back two parts — only Part A is readable by Alice
Part A — TGS Session Key
🔑 Encrypted with: Alice's NTLM hash
Alice uses her NTLM hash to decrypt this → gets the TGS Session Key
Contains: a random session key
Alice decrypts this using her NTLM hash
She stores it in memory
Used later to prove she owns the TGT when talking to TGS
Part B — TGT (Ticket Granting Ticket)
🔑 Encrypted with: KRBTGT hash
KDC's master secret — only the KDC can decrypt this. Alice CANNOT read it.
Contains:
 • Alice's username
 • Alice's group memberships
 • TGS Session Key (same as Part A)
 • Valid for 10 hours
Alice just stores this blob and passes it to TGS later — she can't read or modify it
📦 Stored in memory
Windows:
LSASS process memory
lsass.exe
Linux:
Credential cache file
/tmp/krb5cc_[uid]
★ Golden Ticket:
Steal the KRBTGT hash → forge a TGT for any user (even Domain Admin) — valid for years
Single Sign-On: Alice now has a TGT valid 10 hours. Every time she needs to access a service (file server, Exchange, SQL…), she uses this TGT to get a service-specific ticket — no re-entering her password.
Step 3 — Get a Service Ticket for FILESERVER
Client → KDC/TGS (TGS-REQ)  ·  KDC/TGS → Client (TGS-REP with Service Ticket)
🖥 Client sends TGS-REQ containing:
① TGT — the opaque blob from Step 2
Client just passes it through — TGS will read it
② SPN — which service she wants
cifs/FILESERVER.corp.local
SPN = unique name that identifies a service on the network
③ Authenticator — username + timestamp
🔑 Encrypted with: TGS Session Key
Enc(TGS_SessionKey, username + timestamp)
Proves Alice owns the TGS Session Key → proves TGT belongs to her
🎫 TGS validates and issues Service Ticket:
① Decrypts TGT using KRBTGT hash
Gets TGS Session Key from inside the TGT
② Decrypts Authenticator using that session key
Verifies username matches + timestamp within 5 min
③ Looks up FILESERVER's NTLM hash in AD
Every service account has its own hash stored in AD
④ Issues Service Ticket
🔑 Encrypted with: FILESERVER's NTLM hash
Only FILESERVER has this hash → only it can decrypt and read the ticket
📦 What's inside the Service Ticket (encrypted — only FILESERVER can read)
👤 Alice's username
who is accessing
👥 Group SIDs (PAC)
Domain Users, HR-Team…
used for authorization
🔑 Service Session Key
fresh key for this session
Alice also gets a copy
⏱ Validity: 10 hours
ticket expires after this
★ Kerberoasting: any domain user can request a Service Ticket for any SPN → the ticket is encrypted with the service account's NTLM hash → crack it offline
Step 4 — Authorization: Does Alice get access?
FILESERVER decides — the KDC is completely out of the picture now
What FILESERVER does with the ticket
①
Decrypt the Service Ticket
🔑 Decrypted with: FILESERVER's own NTLM hash
FILESERVER is the only machine with this hash → only it can open this ticket
②
Read the PAC inside the ticket
PAC = list of who Alice is + all her groups
③
Check the ACL of the shared folder
ACL = list of who is allowed to access this resource
④
Compare SIDs from PAC against SIDs in ACL
Any SID match → Access Granted  |  No match → Denied
PAC — inside Alice's Service Ticket
👤 Alice's SID: S-1-5-21-...-1105
👥 Domain Users SID: S-1-5-21-...-513
👥 HR-Team SID: S-1-5-21-...-1120
↕ compared against
ACL — on \\FILESERVER\HR-Share
✔ HR-Team SID → Read allowed
✔ Admins SID   → Full control
✘ Everyone     → No access
HR-Team SID matches ✔
→ Alice gets Read access to \\FILESERVER\HR-Share
Authentication (KDC)
Answers: "Who is Alice?"
Issues TGT + Service Ticket.
Done — KDC steps away.
Authorization (Service)
Answers: "What can Alice access?"
Checks PAC SIDs vs ACL SIDs.
No KDC involved — service decides alone.
Attack implication
Silver Ticket = forge the Service Ticket with fake group SIDs in the PAC → service trusts it → unauthorized access!

Overview
Kerberos in one line
A trusted third-party (the KDC) issues encrypted tickets so users can prove their identity to services without sending passwords over the network.
The 4 actors
🖥 Client — Alice's laptop
🔐 AS — Verifies identity, issues TGT
🎫 TGS — Issues service-specific tickets
🗄 Service — Resource being accessed
KDC = AS + TGS
Both live on the Domain Controller. AS handles login and TGT issuance. TGS handles service ticket issuance. The AD database stores NTLM hashes for all accounts.
Key properties
✔ Password never on the wire
✔ Single Sign-On (SSO)
✔ Mutual authentication
✔ Tickets expire automatically
✔ Replay protection via timestamps
NTLM Hash
MD4(UTF-16LE("password")) = 16 bytes.
Acts as the long-term symmetric key. KDC stores it in AD (ntds.dit). Never sent on the wire.
Pass-the-Hash
Attacker steals NTLM hash from LSASS memory or ntds.dit → uses it directly to authenticate. No need to crack the password.
AES key (modern)
Derived via string2key() + PBKDF2 with 4096 iterations. Salt = REALM + username. Much harder to crack offline than NTLM/RC4.
Both sides derive the same key
Client derives it from the typed password. KDC looks it up in AD. Neither sends it to the other — it's a shared secret.
AS-REQ
Client sends: username, realm, encrypted timestamp (Enc with NTLM hash), random nonce. This is pre-authentication — proves Alice knows the password.
5-minute clock skew
Kerberos checks the decrypted timestamp. If it's more than 5 min off → rejected. This prevents replay attacks. All machines must sync to a time source (NTP).
AS-REP Roasting
If "Do not require Kerberos preauthentication" is set → KDC issues TGT to anyone. Attacker requests it → cracks Part A (enc'd with user's hash) offline.
GetNPUsers.py Rubeus asreproast
TGT contents
Username, groups, IP, validity (~10h), TGS Session Key — all encrypted with the KRBTGT account's NTLM hash. KRBTGT is a special service account that exists on every Domain Controller. Client can't read the TGT.
Part A (TGS Session Key)
Encrypted with Alice's NTLM hash. She decrypts this and stores it. Used later to prove she has the TGT when talking to TGS.
Storage
Windows: LSASS.exe memory
Linux: /tmp/krb5cc_[uid]

Extract with: Mimikatz Rubeus dump
Golden Ticket
Steal the KRBTGT account's NTLM hash → forge a TGT for ANY user (including Domain Admin) valid for years. Since TGTs are signed with the KRBTGT account's NTLM hash, owning that hash = owning the entire domain.

Persists even after the real user's password is reset.
Fix: rotate KRBTGT account password twice (invalidates all existing TGTs).
TGS-REQ contents
TGT (opaque) + SPN of target service + Authenticator (username+timestamp enc'd with TGS Session Key) + nonce.
What is an SPN?
Service Principal Name — unique ID for a service instance.
cifs/SERVER.corp.local
http/web:80
MSSQLSvc/db:1433
Authenticator
Proves Alice owns the TGT. TGS uses TGS Session Key (from inside TGT) to decrypt it and verify. TGS also checks replay cache — same Authenticator can't be used twice.
Kerberoasting
Any authenticated user can request a service ticket for any SPN. Ticket is enc'd with service account's hash. Attackers request it, crack offline (especially RC4).
Rubeus kerberoast GetUserSPNs.py
Service Ticket contents
Username, group SIDs (PAC), Service Session Key, validity — all encrypted with service account's NTLM hash. Only that service can read it.
PAC — Privilege Attribute Certificate
Embedded in the ticket. Contains user SID, group SIDs, account flags, KDC signature. Service reads PAC to make authorization decisions — no KDC needed.
Silver Ticket
Steal service account's NTLM hash → forge Service Ticket → bypass TGS entirely. Stealthy — KDC never contacted. Fix: use gMSA (auto-rotating 240-char passwords).
Client also gets
Service Session Key (enc'd with TGS session key). Client decrypts, stores, uses it to encrypt the Authenticator when talking directly to the service.
AP-REQ to service
Client sends: Service Ticket (opaque) + Authenticator (username+timestamp enc'd with Service Session Key). Service validates both independently.
Service validation
① Decrypt ticket with own key → get Service Session Key + PAC
② Decrypt Authenticator → verify user+time
③ Check replay cache
④ Read PAC → check ACL → grant/deny
Mutual Auth (AP-REP)
Service can respond with AP-REP encrypted with Service Session Key. Client decrypts → confirms it's the real service, not an impostor.
KDC not involved
Steps 1–4 are the setup. This final step happens directly between client and service. The KDC has no visibility — this is why Silver Tickets are hard to detect via KDC logs.
SSO in action
After AS-REP, TGT is cached. For every new service Alice needs (Exchange, SharePoint, SQL…), only TGS-REQ → AP-REQ repeat — no password re-entry for 10 hours.
Attack quick-ref
🔴 Golden Ticket — KRBTGT hash
🔴 Silver Ticket — service hash
🔴 Kerberoasting — SPN ticket crack
🔴 AS-REP Roasting — no pre-auth
🔴 Pass-the-Ticket — steal TGT/ST
🔴 Unconstrained Delegation — TGT theft
Defense quick-ref
🛡 Disable RC4, enforce AES only
🛡 Require pre-auth for all accounts
🛡 gMSA for service accounts
🛡 Protected Users group
🛡 Monitor events 4768/4769/4771
🛡 Rotate KRBTGT twice on breach
Authentication (KDC)
Verifies identity using NTLM hash + encrypted timestamp. Issues TGT. Password never travels. Result: "KDC confirms I am Alice."
Authorization — Service decides, not KDC
Step 1: Service decrypts the ticket with its own NTLM hash
Step 2: Reads the PAC inside — contains Alice's SID + all her Group SIDs
Step 3: Looks at the ACL of the resource (e.g. shared folder)
Step 4: Compares — does any SID in the PAC appear in the ACL?
  ✔ Match found → Access Granted
  ✘ No match → Access Denied

The KDC is never contacted. It only issued the ticket — the service makes the access decision entirely on its own.
Why the separation matters
Authz is done by the service → a Silver Ticket can forge the PAC to include fake group memberships → attacker grants themselves access without KDC ever knowing.
Delegation types
Unconstrained: service stores full TGTs
Constrained: limited to specific targets
RBCD: target controls who can delegate

Unconstrained = major attack vector!
AES256 (recommended)
etype 18. Key derived via string2key + PBKDF2 (4096 iter). Salt = REALM+username. Computationally expensive → Kerberoasting much harder.
RC4-HMAC (etype 23)
Uses NTLM hash directly as RC4 key. No PBKDF2 → billions of guesses/sec offline. Kerberoasting targets this. Disable via GPO: "Configure encryption types allowed for Kerberos."
Authenticated encryption
Every message = Encrypt + HMAC. Confidentiality AND integrity. Tampering is detected. Replay protection via timestamp + nonce in each Authenticator.
Best practice
Allow AES128 + AES256 only. Disable RC4/DES. Use gMSA for services (240-char auto-rotating password → Kerberoasting impossible). Strong passwords for regular accounts.
